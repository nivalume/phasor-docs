从第一性原理看：一个向量化回测循环要回答什么

先不看代码。“按信号买卖”在每根 K 线上要做的事情，比看起来多得多。

1. 时间方向上不能并行

第 t 根 K 线的状态（现金、仓位、负债、止损）取决于第 t − 1 根：state[t] = f(state[t−1], bar[t])。这条依赖切不断，所以“向量化”在这里不是 SIMD， 而是把很多条互不相关的时间序列放在列轴上一起跑。撮合内核是一棵有十几个提前返回的分支树，不同的列几乎每根 K 线都走不同的分支，SIMD 的通道会不断分叉； 按列（更准确地说按账户组）分给线程才是对的。SIMD 属于因子和分析层，那里没有这种依赖。

2. 共享资金把“列”变成“组”

默认每列有自己的现金，是一次独立的回测。几个标的共用一个账户时，它们就不再是 N 次模拟，而是一次覆盖 N 个标的的模拟：同一根 K 线里必须按某个顺序执行， 因为每笔成交都会改变后面的单能花多少钱。并行的单位于是从列变成组；单个共享账户就是一个单位，这是共享余额本身决定的，不是实现的缺陷。

3. 先卖后买

一次调仓里，买单如果排在为它筹钱的卖单前面，就会因为现金不够被拒——而且是静默的，那一列只是没交易。这是共享资金回测里最常见的意外。 所以需要一种“自动调用顺序”：按每笔单的近似金额排序，卖（负值）在前、买在后。

4. 一根 K 线要先整体决定，再执行

目标权重（TargetPercent）的单是组合净值的一个比例，而净值取决于所有标的的估值价。如果边执行边估值，同一根 K 线上的单会因为执行先后看到不同的净值。 所以一根 K 线分两遍：先为全组确定价格、估值价和净值，再按调用顺序执行；而且每一笔都按 K 线开始时的净值下单，成交只在 update_value 打开时才改变它。

5. 信号会互相矛盾

同一根 K 线上进场和出场同时为真；做多和做空同时为真；持多仓时来了一个做空信号（是平仓还是反手？）；已经有仓位时又来一个进场（加仓还是忽略？）。 订单数组表达不出这些歧义，信号数组可以。所以信号到订单之间要有一串有固定顺序的解决步骤——顺序换了，留下来的信号就不同。

6. 止损不是观点，是限额

止损触发时，它替换这根 K 线的信号，而不是和它们竞争。触发价也要讲究：开盘就跳空越过止损线，只能按开盘价成交；跟踪止损要在测试之后才更新， 否则一根创新高又回落的 K 线会被自己的回落止损出局。只有收盘价的序列也要能测止损：缺失的开高低由已知的价格补出来。

approx_order_value

Amount × 估值价、Value 原样、Percent 按现金（卖出按持仓价值，平空还要算上释放的保证金）、Target* 减去当前持仓价值。ShortOnly 列的数量先取反。有杠杆或保证金列的运行里，再经 approx_cash_need 换成订单对可用现金的影响：减仓的部分释放，开仓的部分占用（现金列按 1 / leverage，保证金列按初始保证金）。它只用来排序，不影响下单量。

记录按列重排

共享组的成交按执行顺序写出，但每条记录带着自己的列；调用方按 (col, idx) 排序，所以记录的布局和执行顺序无关。

并行：按组切块

Groups::chunks(n_threads) 按总列数的等分点把连续的组切成块，每个线程一块、自带 sink 和计数器；合并时按块的顺序拼接并重新编号，所以和线程怎么交错无关——串行与多线程逐位相同（有测试）。 宽的组自成一块。改下面的组长度和线程数看看。

回调：在 K 线循环里给用户代码留的位置

回调不是事件驱动。循环还是逐根 K 线的那个循环，用同一个撮合内核、写同样的记录；callbacks.rs 只是在每根 K 线的固定位置调用用户代码，让它改掉循环在那里本来要做的事。 回调通过只读的 Context 看账户，改变账户只能靠下单：改变现金或持仓的东西仍然经过内核、落成记录。 入口是 simulate_from_order_func（OrderFunc）和 simulate_from_signal_func（SignalFunc），返回 Run：记录（OrderRecords 或带日志的 Journal）、每组的回调状态和结束时的 SimState。

Flow：继续、跳过、停止

钩子返回 Flow：Continue；SkipSegment，只在 pre_segment 里有意义；StopGroup，这一组不再下单、不再调回调，但剩下的 K 线照常记现金流、持仓费和强平，因为它们属于还开着的仓位。任何钩子返回错误都结束运行。

Context：只读的账户

group、row、cols、cash、free_cash、value（按估值价的组净值，from_orders 里一根之内只有 update_value 才变），按组内下标 k 读 position、debt、locked_cash、close、val_price、stops、order(k)。价格是策略写的价格：from_orders 的列状态里估值价乘过合约乘数，Context 除回去。from_signals 的 adjust 和 signals 在本根价格确定之前调用，val_price 是上一根的。

每组一个 State

pre_group 返回，按组的顺序和记录一起返回（Python 里是 pf.in_outputs）。回调对象本身是共享的 &self，并行入口要求它 Sync；各组照常并行，所以要跨组共享状态的回调得用 Schedule::RowWise。不需要 pre_sim：回调对象在运行前就构造好了。

NoCallbacks：不用时没有代码

两个循环对回调类型泛型。NoCallbacks 把关联常量 ON 设为 false，每个调用点都在 if C::ON 后面，所以普通入口（simulate_from_orders 等都传 &NoCallbacks）跑的那份实例里没有回调的代码。调用回调的辅助函数（callback_order、post_order、decide、segment_end）都是 #[cold]、不内联。

回调不能绕过记录

callback_order 把回调的订单变成 ValidatedOrder：价格的 ±inf 和数组里同义（+inf 当根收盘，−inf 上一根收盘），乘上合约乘数。在没有杠杆和保证金列的运行里要杠杆或保证金账户、或改掉某列的账户类型，都报错：记录要么每笔带余额、要么都不带，这在运行前就定了。

from_signals 的决定走完整条管线

decide 调 adjust 和 signals，得到的 Decision 传进 prepare_order → user_order（以及止损成交后的 follow_up），代替 read_signals 和 size 的读取。有回调时走 EXTENDED 实例，不预先检查 size（要检查的是回调给的）。和非 0 的 from_ago 一起用报错：回调在自己那根上决定，要滞后就在回调里做。

row_wise 与 Group::run_rows

from_orders 的 K 线循环拆成了结构体 Group：Group::new 建好一个组第一根之前的状态（现金、各列 ColumnState、每列的 ValidatedOrder、保证金和乘数，并开好初始持仓；续跑时现金和列状态取自 resume，见续跑），Group::run_rows 跑一段行，Group::finish 交出结束时的 GroupState。 group_loop 对一个组只调一次 run_rows(start..n_rows)，start 不续跑时是 0。Schedule::RowWise（row_wise 函数）先为每组建一个 Group，再对每根 i 依次调各组的 run_rows(i..i + 1)：单线程，每组写自己的缓冲区，最后按组顺序合并，和并行路径合并线程块一样，所以回调不跨组共享状态时，记录和 Schedule::Groups 相同。 run_rows 接受一段行而不是一根，是为了把账户和各个开关在一次调用里只读进局部变量一次，并先把各个 Vec 取成切片，让指针和长度留在寄存器里。

fill! 宏

一笔订单的执行——execute_validated、raise_reject、update_value、写成交和余额、写日志、更新列状态——有两处要用：K 线循环的第二遍，和 flex 路径的 execute。 写成内联函数时，没有回调的循环每根 K 线多花约 23 条指令（列状态被借第二次，结果经 Result 带出来），所以写成宏 fill!：两处共用一份文本，在循环里仍是内联的。 execute 本身 #[inline(always)]，把 post_order 留在里面，成交结果不带出去。加上 FlexArray::get 的标量快路径（见 phasor-core），功能全关时 from_orders 的指令数比 c0fc6b2 多 2.47%，回到 3% 的约束以内，from_signals 少 14.30%（docs/plan.md 的性能记录）。

按风险算仓位：risk_size(value, risk, entry, stop, multiplier) = risk × value / (|entry − stop| × multiplier)，距离为 0 或不是有限数时是 NaN（内核忽略）。在 order 或 signals 里把订单的 size 设成它，size_type 用 Amount。

续跑与状态：从上一次结束的地方接着跑

一次运行在 K 线之间带着的只有两样东西：每个账户组的现金和可用现金，每列的 ColumnState（持仓、负债、锁定现金、估值价、止损、挂着的限价单）。 snapshot.rs 把它们收成 SimState 交回来；下一次运行把它传进 resume，从它的 next_row 开始，不再读 init_cash 和 init_position（初始持仓也不再开）。 在任意一行切开、这样接起来的两段，写出的记录和一次跑完逐位相同，用 OrderRecords::chain 拼好之后顺序也相同（见 phasor-records · 拼接）。

字段内容为什么
source: LoopFromOrders（也是 from_order_func）或 FromSignals状态只能续写它的那个循环：from_orders 的列状态里估值价乘过合约乘数，from_signals 存的是价格，互相换算不精确
next_row续跑的第一行，等于 row_offset + n_rows整次运行的行号，不是数组的下标
levered前一段的记录带不带余额续跑沿用它，记录要么每笔都带余额、要么都不带。前一段不带、这一段却要借钱、保证金或持仓费，报错：要在第一段就带上这些设置（run_levered）
groups: Vec<GroupState>每组 cash、free_cash、按组内顺序的 columns、stoppedstopped 是回调停掉了这一组的交易；续跑的那段仍然不下单

行号是绝对的

状态里的行号都是整次运行的：时间止损的 td_row、dt_row，挂单的 created、last_row。循环仍从 0 读自己的数组，只在状态和记录进出时换算：group_for 减去 row_offset（早于数组起点的变成 0），Group::finish / snapshot::finish 加回去，记录在 finish_run 里 shift_rows(row_offset)。表示“永不”的 usize::MAX 不动；挂单槽位空着时它的两个行号只是占位，也不动，只有挂着的限价单的行号会移。

resume 与 row_offset

两种续法。只给 resume：数组还是整段历史，从 next_row 跑到末尾，前面的行只被回看。再给 row_offset：数组覆盖 row_offset..row_offset + n_rows，长历史可以一段一段跑，不必整段放进内存。这时数组要带上 next_row 之前被回看的几行：price = −inf 读上一根收盘，from_ago 读更早的；不带的话，这一段开头几根读到 NaN。start_in 检查来源循环、组数，以及 next_row 落在数组覆盖的行内；group_for 检查每组的列数。

随机数用整次运行的行

随机拒单的抽签是 uniform(seed, i + row_offset, col)。用数组下标 i 的话，同一根 K 线在分段运行里会抽到另一个数，被拒的单就不同了。这和“串行与多线程逐位相同”是同一条规则：随机数只能是 (seed, 行, 列) 的函数。

不在状态里的

回调自己的状态：带回调的运行续跑时再调一次 pre_group，带状态的回调在那里重建。记录也不在：状态是下一根要的，记录是过去做的。

Run

simulate_from_orders_run / simulate_from_signals_run（按组分到 n_threads 个线程）返回 Run { records, states, last_state }；simulate_from_order_func / simulate_from_signal_func 也改成返回 Run，states 是每组的回调状态，没有回调时是 ()。原来的四个入口仍然只返回记录。

字节

to_bytes 写小端二进制：魔数 PHSS、版本 1、来源、next_row、levered，然后每组、每列的每个字段。from_bytes 拒绝别的魔数或版本、截断的、后面还多出字节的。库 crate 不写文件，字节写到哪里是调用方的事（Python 的 phasor.save）。

不能绕开的规则

串行与多线程逐位相同

每个组写自己的缓冲区，记录 id 在按组顺序合并之后才分配；随机拒单的随机数是 (seed, row, col) 的函数（row 是整次运行的行号，分段运行也一样），只在概率不为 0 时生成。任何依赖线程交错的东西都会破坏这一点。

现金的变化必须是记录

入金、分红、收益、持仓费、穿仓核销和初始持仓的成本都写成 CashRecords，强平写成带 liquidation 标记的成交，因为分析层只从记录重建余额。只改了循环里的 cash 而不写记录，净值曲线会悄悄错。保证金结算是例外：它只在持仓和现金之间挪钱，不改变权益，所以不留记录。

阶段的顺序是语义

先多头进出冲突、再空头进出冲突、再多空冲突、最后反向进场；先测止损再跟踪；先确定全组价格再执行。换顺序就会换掉留下来的信号或成交，fixture 会抓到。tests/fixtures/*.tsv 不能为了让改动通过而重新生成。

保持 Send、无全局状态

参考的事件驱动引擎把状态放在进程全局的 Rc<RefCell<..>> 后面，只能顺序扫描；这里每个引擎实例都必须 Send，这是代码库的硬约束（lib.rs 模块文档）。

src/cash.rs · src/random.rscash 是公开模块：开盘的入金与分红（deposit、pay_dividends、at_open）、收盘的收益（earn，负数封顶于可用现金）；book 给自定义循环记任意一种现金流并写记录。random：不内联的 uniform，转调 phasor_core::random::uniform(seed, row, col)，只在 reject_prob > 0 时用到。
src/margin.rs保证金列的 owed、unsettled、settle：每根 K 线把盈亏结算进现金，成本移到估值价；逐仓列不结算。
src/holding.rsRates、Held、charge：收盘按订单之后的持仓收资金费、隔夜融资、借款利息、借券费，不封顶，按 mark_price（否则收盘价）乘合约乘数算名义价值。逐仓列从自己的保证金（locked_cash）付，可用现金不变；账户现金低于 0、超出现金列多头借款的部分按第一列的 debt_rate 计息，记到第一列。
src/liquidation.rsInputs、Column、test（路径从开盘到不利极值或标记价格，权益和维持保证金按 α 线性，求第一次跌破的点；分档 maintenance_margin_tiers 时维持保证金分段线性，用二分法求）、fill（TargetAmount(0) 或部分平仓、liquidation_fee、记录标记）、ROUNDS = 64 与 step_size（liquidation_step 的部分强平，沿 K 线剩下的路径继续检查）、write_off / write_off_account（穿仓核销）。cash_maintenance_margin 让借钱或借券的现金列和保证金列一起强平。路径上的价格乘合约乘数。两个循环各有一个不内联的 liquidate，ADL（auto_deleverage 标记的 K 线上按标记价格、不收手续费平掉保证金列开着的仓位，不看盈亏；交易所先平哪些仓位，由调用方标哪些 K 线表达）也在那里。
